# Spike report: CubeCL GEMM for dense M2L shapes (Phase 0 / T6)

Date: 2026-09-29. Brief: [docs/phase0/T6-cubecl-gemm-spike.md](../../docs/phase0/T6-cubecl-gemm-spike.md).
Raw output: [results-m3max.md](results-m3max.md). Summary tables and the roofline model are
generated by [analyse.py](analyse.py) from that file.

## Summary

- **f32, measured on Metal (M3 Max GPU):** dense GEMM is the Phase 4 default for the f32
  path (p ≤ 8, design doc §6.2). The library matmul (`Strategy::Auto`, which picks the
  simdgroup-matrix CMMA kernel) reaches 3.5–4.4 TFLOP/s for p ≥ 8 and B ≥ 1e4. At p = 4
  the library falls back to its scalar path and gets only 0.3 TFLOP/s; the hand-written
  comptime-p kernel gets 3.0 TFLOP/s there, at the memory roofline. So Phase 4 needs both:
  library CMMA for p ≥ 8 and a hand-written kernel for small p.
- **f64 on data-centre CUDA cards, predicted (not measured):** dense GEMM is the
  provisional default for p ≤ 8 and rotation for p ≥ 12, with the crossover to be set by
  autotune. The prediction rests on a roofline model with efficiency factors from Metal;
  see "Roofline prediction". At p = 8, dense wins unless rotation M2L reaches more than
  about 13% of f64 peak. At p = 12 and 16 rotation wins once it exceeds 4–5%.
- **Three CubeCL facts matter more than the numbers:**
  1. CubeCL 0.10.0 disables f64 on its CUDA backend (`cubecl-cpp` 0.10.0,
     `src/shared/base.rs`: f64 is commented out of `register_supported_types` with "Causes
     CUDA_ERROR_INVALID_VALUE for matmul"). 0.11.0-pre.4 re-enables it. **The pinned
     version cannot run f64 on CUDA**; the Phase 4 f64 path needs 0.11 (or a patch).
  2. Neither 0.10.0 nor 0.11.0-pre.4 has an FP64 tensor-core (DMMA) path: CUDA MMA
     combinations are F16, BF16 and TF32 only. An f64 GEMM in CubeCL therefore runs on
     plain FMA units, so the "without FP64 tensor cores" roof applies, and the A100/H100
     f64 peak is effectively halved.
  3. The library's scalar ("unit") path, which is what f64 would get on CUDA, reaches only
     9–14% of the roofline on Metal, against 19–36% for the hand-written kernel. **Phase 4
     should plan a hand-written comptime-p f64 GEMM kernel**, not rely on the library for f64.
- **CPU runtime:** it verifies correctness in f64 (every f64 result is bit-identical to
  the reference). As a throughput backend it is weak for the library (≤ 10 GFLOP/s in f64,
  about 1% of peak); the hand-written register-tiled kernel reaches 32–200 GFLOP/s
  (4–26%). It is not used as the efficiency source for the GPU prediction.

The recommended next step (preferred, not required) is one run of this benchmark on an
A100 or H100 with CubeCL 0.11 before Phase 4 fixes the f64 default; see "CUDA run".

### Method

- C = A X, A of shape Nc × Nc, Nc = (p+1)², X and C of shape Nc × B, all row-major and
  contiguous; p ∈ {4, 8, 12, 16}, B ∈ {1e3, 1e4, 1e5}. Inputs are uniform in [-1, 1) from a
  fixed-seed generator.
- Timing: a sync costs about 1.5 ms on wgpu/Metal regardless of the kernel, so launches
  are queued in batches (doubled until a batch takes ≥ 50 ms), one sync per batch, and the
  median time per launch over at least 5 batches (about 1 s) is reported. This matches an
  FMM pass, which queues many kernels between syncs. Kernel compilation is excluded
  (warm-up launch).
- Correctness: every measured result is read back and compared with a plain-Rust GEMM in
  f64 on the same (rounded) inputs, by max-norm relative error. Tolerance 1e-12 for f64,
  1e-5 for f32. **All 177 measured results pass** (f32: at most 8.1e-7; f64: 0, because
  both sides sum in the same order without fused multiply-adds).
- Implementations:
  - `lib:<strategy>`: `cubek_matmul::launch::launch_ref` with `Strategy::Auto` (the default
    for a caller), `SimpleUnit`, `DoubleUnit` (scalar units), `SimpleCyclicCmma`,
    `DoubleCyclicCmma` (plane-level matrix units: simdgroup matrices on Metal).
  - `tiled-smem`: hand-written, GPU-shaped. Cubes of 16 × 16 units, shared-memory tiles
    of A and X (k depth 16), each unit accumulates tm × 4 outputs in registers. Nc and tm
    are comptime (tm = 2, 6, 11, 10 for p = 4, 8, 12, 16, so one or two row blocks cover
    all rows and X is read at most twice).
  - `tiled-reg-cols` / `tiled-reg-rows`: hand-written, one unit per 4 × 8 register tile of
    C, columns vectorised (4 lanes), operands read straight from global memory (caches do
    the reuse), no shared memory or barriers. Nc comptime. `cols`: a cube spans 32 column
    tiles of one row block (coalesced loads of X on a GPU). `rows`: a cube spans all row
    blocks of one column strip (the strip of X stays in cache on a CPU).
- Tests (`cargo test -p nd-fmm-spike-cubecl-gemm --release`): the reference against a
  triple loop; both hand-written kernels against the reference on the CPU runtime, f32 and
  f64, for shapes that hit every guard (p ∈ {1, 4, 8}, B ∈ {12, 68, 100}).

Observations:

- **Run-to-run variance on Metal is about ±25%.** The table is from one sustained sweep
  (conservative). Three later repeat runs of p = 16, B = 1e5 gave 4.2–4.5 TFLOP/s for the
  library (sweep: 3.5; an earlier short run: 5.3) and 3.2–3.3 for the hand-written kernels
  (sweep: 2.5–2.7). The ranking of implementations did not change. The laptop's power and
  thermal management is the likely cause; `pmset` recorded no thermal warning.
- **p = 4, B = 1e5 on Metal exceeds the DRAM roofline** (2978 vs 2500 GFLOP/s): the 20 MB
  working set stays in the system-level cache between repeated GEMMs. The DRAM bound is the
  relevant one for a real FMM pass, which streams different data each time.
- **Library CMMA needs Nc ≳ 64:** at p = 4 (Nc = 25) the CMMA strategies are rejected
  ("required feature is unavailable: plane dimension") and `Auto` falls back to the scalar
  unit path.
- **B = 1e3 is launch- and occupancy-limited on Metal** (13 MFLOP at p = 8 takes 9–22 µs).
  Batching many M2L offsets into one launch matters more than the GEMM kernel at that size.
- **CPU runtime quirks:** the 256-unit shared-memory kernel is emulated very slowly (one
  p = 4, B = 1e3 GEMM took 33 s), so `tiled-smem` is skipped there (it is still tested there
  for correctness on small shapes). The runtime's default 64 MB worker stack overflows at
  p = 16, B = 1e5; the binary sets `CUBECL_CPU_STACK_MB=1024`. The library's f32 kernels
  for B = 1e4 did not finish compiling in over 5 minutes, twice (single-threaded in
  `cubecl_opt`'s `InlineAssignments` pass); CPU f32 was therefore run with `--no-lib`.
- **On the CPU runtime, the cube layout matters:** `tiled-reg-rows` keeps a strip of X in
  cache and is 3.4× faster than `tiled-reg-cols` at p = 16, B = 1e5 (125 vs 37 GFLOP/s);
  on Metal it is the other way round (`cols` 2542, `rows` 931). The Phase 4 kernels need a
  per-backend layout choice.

## Roofline prediction for data-centre CUDA cards

Everything in this section is a model, not a measurement.

### Assumptions

1. Card figures from NVIDIA's datasheets ([A100](https://www.nvidia.com/en-us/data-center/a100/),
   [H100](https://www.nvidia.com/en-us/data-center/h100/)):

   | card | f64 | f64 with FP64 tensor cores | f32 | memory bandwidth |
   | --- | --- | --- | --- | --- |
   | A100 SXM 80 GB | 9.7 TFLOP/s | 19.5 TFLOP/s | 19.5 TFLOP/s | 2,039 GB/s |
   | H100 SXM | 34 TFLOP/s | 67 TFLOP/s | 67 TFLOP/s | 3.35 TB/s |

   NVIDIA's sparsity footnote applies to TF32 and lower precisions, not to FP64.
2. **CubeCL cannot use FP64 tensor cores** (no F64 MMA combination in 0.10.0 or
   0.11.0-pre.4), so the "no TC" roof is the one CubeCL can reach. The TC column is a
   hypothetical upper bound for a future DMMA path.
3. An implementation reaches the same fraction of the (DRAM) roofline bound on the card
   as it does on the M3 Max GPU for the same p and B = 1e5, whichever roof binds.
   - Central: the hand-written kernels on Metal (19–36% for p ≥ 8), because CubeCL's f64
     path on CUDA would be a non-tensor-core kernel and the hand-written kernel is the
     better such kernel.
   - Low: the library's scalar unit path on Metal (9–14%), which is what
     `Strategy::Auto` would pick for f64 on CUDA (CMMA has no f64).
   - Hypothetical TC: the library CMMA path on Metal (24–47% for p ≥ 8) applied to the
     FP64 tensor-core roof.

   The CPU-runtime f64 efficiencies (16–21% for the hand-written kernel) are close to the
   central Metal ones, but they come from an MLIR CPU backend and are not used for the GPU.
4. Flops per M2L pair: dense 2(p+1)⁴ (one Nc × Nc matrix–vector product). Rotation
   (point-and-shoot, design doc §4): two rotations of Σₙ(2n+1)² ≈ (4/3)(p+1)³ multiply-adds
   and a coaxial shift of about (2/3)(p+1)³, i.e. (10/3)(p+1)³ multiply-adds = (20/3)(p+1)³
   flops. The dense/rotation flop ratio is therefore 0.3(p+1). If the design doc's
   (10/3)(p+1)³ were meant as flops rather than multiply-adds, the ratio doubles and every
   break-even efficiency below halves.
5. Rotation efficiency is unknown (no rotation M2L exists yet), so the result is stated as
   the break-even rotation efficiency, the number a later measurement confirms or overturns.

So in f64, p = 4 is memory-bound on both cards, p = 8 is compute-bound on the A100 and at

### Dense against rotation M2L in f64

When both are compute-bound, dense GEMM wins exactly when its efficiency exceeds
0.3(p+1) times rotation's; this ratio does not depend on the card. The table gives the
break-even rotation efficiency, the fraction of f64 peak (no TC) that a rotation M2L must
reach to match the predicted dense time. Dense wins if rotation stays below it.

| card | p | dense ns per pair (central) | break-even rotation efficiency (central) | (low) |
|---|---|---|---|---|
| A100 SXM | 8 | 3.81 | 13.2% | 5.1% |
| A100 SXM | 12 | 27.7 | 5.4% | 2.3% |
| A100 SXM | 16 | 89.6 | 3.8% | 1.7% |
| H100 SXM | 8 | 1.09 | 13.1% | 5.0% |
| H100 SXM | 12 | 7.91 | 5.4% | 2.3% |
| H100 SXM | 16 | 25.6 | 3.8% | 1.7% |

At p = 4 both methods are memory-bound. Each pair must at least read Nc inputs and write
Nc outputs, and the dense GEMM does little more, so dense GEMM ties or wins there. The
break-even figures from `analyse.py` for p = 4 (20–44%) ignore rotation's memory floor and
are not meaningful.

For comparison, the measured f32 case on the M3 Max GPU (best dense implementation,
B = 1e5) gives break-even rotation efficiencies of 13.9%, 9.8%, 7.1% and 4.8% for
p = 4, 8, 12, 16.

## Recommendation

**f32 (measured on Metal):** dense-GEMM M2L is the Phase 4 default for the f32 path
(p ≤ 8). Use the library matmul (`Strategy::Auto`, CMMA) for p ≥ 8 and a hand-written
comptime-p kernel for small p, where the library's scalar fallback is 10× slower. Dense
wins against rotation unless a rotation M2L reaches about 10% (p = 8) to 14% (p = 4) of f32
peak, which is unlikely for its short, irregular per-degree loops.

**f64 on A100/H100 (provisional, from the roofline model):**
- Dense GEMM as the default for p ≤ 8 (break-even rotation efficiency about 13% at p = 8);
  rotation as the default for p ≥ 12 (break-even 4–5%). The crossover near p ≈ 10 is left
  to autotune, as the design doc already plans (§4).
- The f64 dense path must be a hand-written comptime-p kernel: the library offers only its
  scalar path for f64 (no FP64 MMA), which the model puts 2.2–2.6× below the hand-written
  kernel. An FP64 tensor-core path would lift dense GEMM by up to about 2.6× at p ≥ 8
  (1.3× at p = 8 on the H100, which sits at its ridge), but CubeCL does not have one.
- The pinned CubeCL 0.10.0 cannot run f64 on CUDA at all. Before Phase 4, either move the
  workspace pin to 0.11 once it is released (a separate decision; the CubeCL API changes)
  or confirm that `--force-f64` works on 0.10.

What would change this: a measured rotation M2L efficiency (it moves the crossover p
directly), a CUDA measurement of the hand-written f64 kernel (it replaces the central
efficiency), and the O(p⁴) memory of dense operators at high p (design doc §9.1), which
favours rotation independently of speed.

## CUDA run (preferred before Phase 4, not required)

The `cuda` feature builds the same benchmark for CUDA. Here it was only type-checked
(`cargo check -p nd-fmm-spike-cubecl-gemm --release --no-default-features --features cuda`
succeeds on macOS); it was not linked or run, as this machine has no CUDA driver. On an A100
or H100:

```sh
cargo run -p nd-fmm-spike-cubecl-gemm --release --no-default-features --features cuda -- --backends cuda
```

On CubeCL 0.10.0, f64 is reported unsupported and skipped; `--force-f64` tries it anyway.
The meaningful f64 run needs the workspace pin moved to CubeCL 0.11 (and `cubek-matmul`
to its matching release), which is a separate decision. Add the measured rows next to the
predictions above; the numbers to compare are the central efficiency of the hand-written
kernel (19–36%) and the dense ns per pair.

## Reproducing

```sh
# Tests (CPU runtime; downloads the tracel-llvm bundle on the first build)
cargo test -p nd-fmm-spike-cubecl-gemm --release
# Full sweep on Metal, then the CPU runtime (f64, then f32 without the library)
cargo run -p nd-fmm-spike-cubecl-gemm --release -- --backends metal
cargo run -p nd-fmm-spike-cubecl-gemm --release -- --backends cpu --precisions f64
cargo run -p nd-fmm-spike-cubecl-gemm --release -- --backends cpu --precisions f32 --no-lib
# Summary and roofline tables
python3 spikes/cubecl-gemm/analyse.py spikes/cubecl-gemm/results-m3max.md
```

Metal needs a process with GPU access (it fails inside a macOS sandbox with "No possible
adapter available").
