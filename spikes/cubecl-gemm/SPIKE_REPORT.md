# Spike report: CubeCL GEMM for dense M2L shapes (Phase 0 / T6)

Date: 2026-09-29. Brief: [docs/phase0/T6-cubecl-gemm-spike.md](../../docs/phase0/T6-cubecl-gemm-spike.md).
Raw output: [results-m3max.md](results-m3max.md). Summary tables and the roofline model are
generated by [analyse.py](analyse.py) from that file.

**Update 2026-10-03 (Phase 4 T2):** the workspace now pins CubeCL 0.11.0-pre.4, and the
spike was ported and re-measured; see "CubeCL 0.11.0-pre.4" at the end. The CPU-runtime
figures below are from 0.10.0 and are superseded there; the Metal figures still hold.

**Update 2026-10-06 (Phase 4S T2):** the spike ran on CUDA, on the H100 of a GH200; see
"CUDA on GH200" at the end. The roofline predictions below are compared with it there.

## Summary

- **f32, measured on Metal (M3 Max GPU):** dense GEMM is the Phase 4 default for the f32
  path (p ≤ 8, design doc §6.2). The library matmul (`Strategy::Auto`, which picks the
  simdgroup-matrix CMMA kernel) reaches 3.5–4.4 TFLOP/s for p ≥ 8 and B ≥ 1e4. At p = 4
  the library falls back to its scalar path and gets only 0.3 TFLOP/s; the hand-written
  comptime-p kernel gets 3.0 TFLOP/s there, at the memory roofline. So Phase 4 needs both:
  library CMMA for p ≥ 8 and a hand-written kernel for small p.
- **f64 on data-centre CUDA cards, predicted (not measured):** dense GEMM is the
  provisional default for p ≤ 8 and rotation for p ≥ 12, with the crossover to be set by
  autotune. The prediction rests on a roofline model with efficiency factors from Metal;
  see "Roofline prediction". At p = 8, dense wins unless rotation M2L reaches more than
  about 13% of f64 peak. At p = 12 and 16 rotation wins once it exceeds 4–5%.
- **Three CubeCL facts matter more than the numbers:**
  1. CubeCL 0.10.0 disables f64 on its CUDA backend (`cubecl-cpp` 0.10.0,
     `src/shared/base.rs`: f64 is commented out of `register_supported_types` with "Causes
     CUDA_ERROR_INVALID_VALUE for matmul"). 0.11.0-pre.4 re-enables it. **The pinned
     version cannot run f64 on CUDA**; the Phase 4 f64 path needs 0.11 (or a patch).
  2. Neither 0.10.0 nor 0.11.0-pre.4 has an FP64 tensor-core (DMMA) path: CUDA MMA
     combinations are F16, BF16 and TF32 only. An f64 GEMM in CubeCL therefore runs on
     plain FMA units, so the "without FP64 tensor cores" roof applies, and the A100/H100
     f64 peak is effectively halved.
  3. The library's scalar ("unit") path, which is what f64 would get on CUDA, reaches only
     9–14% of the roofline on Metal, against 19–36% for the hand-written kernel. **Phase 4
     should plan a hand-written comptime-p f64 GEMM kernel**, not rely on the library for f64.
- **CPU runtime:** it verifies correctness in f64 (every f64 result is bit-identical to
  the reference). As a throughput backend it is weak for the library (≤ 10 GFLOP/s in f64,
  about 1% of peak); the hand-written register-tiled kernel reaches 32–200 GFLOP/s
  (4–26%). It is not used as the efficiency source for the GPU prediction.

The recommended next step (preferred, not required) is one run of this benchmark on an
A100 or H100 with CubeCL 0.11 before Phase 4 fixes the f64 default; see "CUDA run".

### Method

- C = A X, A of shape Nc × Nc, Nc = (p+1)², X and C of shape Nc × B, all row-major and
  contiguous; p ∈ {4, 8, 12, 16}, B ∈ {1e3, 1e4, 1e5}. Inputs are uniform in [-1, 1) from a
  fixed-seed generator.
- Timing: a sync costs about 1.5 ms on wgpu/Metal regardless of the kernel, so launches
  are queued in batches (doubled until a batch takes ≥ 50 ms), one sync per batch, and the
  median time per launch over at least 5 batches (about 1 s) is reported. This matches an
  FMM pass, which queues many kernels between syncs. Kernel compilation is excluded
  (warm-up launch).
- Correctness: every measured result is read back and compared with a plain-Rust GEMM in
  f64 on the same (rounded) inputs, by max-norm relative error. Tolerance 1e-12 for f64,
  1e-5 for f32. **All 177 measured results pass** (f32: at most 8.1e-7; f64: 0, because
  both sides sum in the same order without fused multiply-adds).
- Implementations:
  - `lib:<strategy>`: `cubek_matmul::launch::launch_ref` with `Strategy::Auto` (the default
    for a caller), `SimpleUnit`, `DoubleUnit` (scalar units), `SimpleCyclicCmma`,
    `DoubleCyclicCmma` (plane-level matrix units: simdgroup matrices on Metal).
  - `tiled-smem`: hand-written, GPU-shaped. Cubes of 16 × 16 units, shared-memory tiles
    of A and X (k depth 16), each unit accumulates tm × 4 outputs in registers. Nc and tm
    are comptime (tm = 2, 6, 11, 10 for p = 4, 8, 12, 16, so one or two row blocks cover
    all rows and X is read at most twice).
  - `tiled-reg-cols` / `tiled-reg-rows`: hand-written, one unit per 4 × 8 register tile of
    C, columns vectorised (4 lanes), operands read straight from global memory (caches do
    the reuse), no shared memory or barriers. Nc comptime. `cols`: a cube spans 32 column
    tiles of one row block (coalesced loads of X on a GPU). `rows`: a cube spans all row
    blocks of one column strip (the strip of X stays in cache on a CPU).
- Tests (`cargo test -p nd-fmm-spike-cubecl-gemm --release`): the reference against a
  triple loop; both hand-written kernels against the reference on the CPU runtime, f32 and
  f64, for shapes that hit every guard (p ∈ {1, 4, 8}, B ∈ {12, 68, 100}).

Observations:

- **Run-to-run variance on Metal is about ±25%.** The table is from one sustained sweep
  (conservative). Three later repeat runs of p = 16, B = 1e5 gave 4.2–4.5 TFLOP/s for the
  library (sweep: 3.5; an earlier short run: 5.3) and 3.2–3.3 for the hand-written kernels
  (sweep: 2.5–2.7). The ranking of implementations did not change. The laptop's power and
  thermal management is the likely cause; `pmset` recorded no thermal warning.
- **p = 4, B = 1e5 on Metal exceeds the DRAM roofline** (2978 vs 2500 GFLOP/s): the 20 MB
  working set stays in the system-level cache between repeated GEMMs. The DRAM bound is the
  relevant one for a real FMM pass, which streams different data each time.
- **Library CMMA needs Nc ≳ 64:** at p = 4 (Nc = 25) the CMMA strategies are rejected
  ("required feature is unavailable: plane dimension") and `Auto` falls back to the scalar
  unit path.
- **B = 1e3 is launch- and occupancy-limited on Metal** (13 MFLOP at p = 8 takes 9–22 µs).
  Batching many M2L offsets into one launch matters more than the GEMM kernel at that size.
- **CPU runtime quirks:** the 256-unit shared-memory kernel is emulated very slowly (one
  p = 4, B = 1e3 GEMM took 33 s), so `tiled-smem` is skipped there (it is still tested there
  for correctness on small shapes). The runtime's default 64 MB worker stack overflows at
  p = 16, B = 1e5; the binary sets `CUBECL_CPU_STACK_MB=1024`. The library's f32 kernels
  for B = 1e4 did not finish compiling in over 5 minutes, twice (single-threaded in
  `cubecl_opt`'s `InlineAssignments` pass); CPU f32 was therefore run with `--no-lib`.
- **On the CPU runtime, the cube layout matters:** `tiled-reg-rows` keeps a strip of X in
  cache and is 3.4× faster than `tiled-reg-cols` at p = 16, B = 1e5 (125 vs 37 GFLOP/s);
  on Metal it is the other way round (`cols` 2542, `rows` 931). The Phase 4 kernels need a
  per-backend layout choice.

## Roofline prediction for data-centre CUDA cards

Everything in this section is a model, not a measurement.

### Assumptions

1. Card figures from NVIDIA's datasheets ([A100](https://www.nvidia.com/en-us/data-center/a100/),
   [H100](https://www.nvidia.com/en-us/data-center/h100/)):

   | card | f64 | f64 with FP64 tensor cores | f32 | memory bandwidth |
   | --- | --- | --- | --- | --- |
   | A100 SXM 80 GB | 9.7 TFLOP/s | 19.5 TFLOP/s | 19.5 TFLOP/s | 2,039 GB/s |
   | H100 SXM | 34 TFLOP/s | 67 TFLOP/s | 67 TFLOP/s | 3.35 TB/s |

   NVIDIA's sparsity footnote applies to TF32 and lower precisions, not to FP64.
2. **CubeCL cannot use FP64 tensor cores** (no F64 MMA combination in 0.10.0 or
   0.11.0-pre.4), so the "no TC" roof is the one CubeCL can reach. The TC column is a
   hypothetical upper bound for a future DMMA path.
3. An implementation reaches the same fraction of the (DRAM) roofline bound on the card
   as it does on the M3 Max GPU for the same p and B = 1e5, whichever roof binds.
   - Central: the hand-written kernels on Metal (19–36% for p ≥ 8), because CubeCL's f64
     path on CUDA would be a non-tensor-core kernel and the hand-written kernel is the
     better such kernel.
   - Low: the library's scalar unit path on Metal (9–14%), which is what
     `Strategy::Auto` would pick for f64 on CUDA (CMMA has no f64).
   - Hypothetical TC: the library CMMA path on Metal (24–47% for p ≥ 8) applied to the
     FP64 tensor-core roof.

   The CPU-runtime f64 efficiencies (16–21% for the hand-written kernel) are close to the
   central Metal ones, but they come from an MLIR CPU backend and are not used for the GPU.
4. Flops per M2L pair: dense 2(p+1)⁴ (one Nc × Nc matrix–vector product). Rotation
   (point-and-shoot, design doc §4): two rotations of Σₙ(2n+1)² ≈ (4/3)(p+1)³ multiply-adds
   and a coaxial shift of about (2/3)(p+1)³, i.e. (10/3)(p+1)³ multiply-adds = (20/3)(p+1)³
   flops. The dense/rotation flop ratio is therefore 0.3(p+1). If the design doc's
   (10/3)(p+1)³ were meant as flops rather than multiply-adds, the ratio doubles and every
   break-even efficiency below halves.
5. Rotation efficiency is unknown (no rotation M2L exists yet), so the result is stated as
   the break-even rotation efficiency, the number a later measurement confirms or overturns.

### Dense against rotation M2L in f64

When both are compute-bound, dense GEMM wins exactly when its efficiency exceeds
0.3(p+1) times rotation's; this ratio does not depend on the card. The table gives the
break-even rotation efficiency, the fraction of f64 peak (no TC) that a rotation M2L must
reach to match the predicted dense time. Dense wins if rotation stays below it.

| card | p | dense ns per pair (central) | break-even rotation efficiency (central) | (low) |
|---|---|---|---|---|
| A100 SXM | 8 | 3.81 | 13.2% | 5.1% |
| A100 SXM | 12 | 27.7 | 5.4% | 2.3% |
| A100 SXM | 16 | 89.6 | 3.8% | 1.7% |
| H100 SXM | 8 | 1.09 | 13.1% | 5.0% |
| H100 SXM | 12 | 7.91 | 5.4% | 2.3% |
| H100 SXM | 16 | 25.6 | 3.8% | 1.7% |

At p = 4 both methods are memory-bound. Each pair must at least read Nc inputs and write
Nc outputs, and the dense GEMM does little more, so dense GEMM ties or wins there. The
break-even figures from `analyse.py` for p = 4 (20–44%) ignore rotation's memory floor and
are not meaningful.

For comparison, the measured f32 case on the M3 Max GPU (best dense implementation,
B = 1e5) gives break-even rotation efficiencies of 13.9%, 9.8%, 7.1% and 4.8% for
p = 4, 8, 12, 16.

## Recommendation

**f32 (measured on Metal):** dense-GEMM M2L is the Phase 4 default for the f32 path
(p ≤ 8). Use the library matmul (`Strategy::Auto`, CMMA) for p ≥ 8 and a hand-written
comptime-p kernel for small p, where the library's scalar fallback is 10× slower. Dense
wins against rotation unless a rotation M2L reaches about 10% (p = 8) to 14% (p = 4) of f32
peak, which is unlikely for its short, irregular per-degree loops.

**f64 on A100/H100 (provisional, from the roofline model):**
- Dense GEMM as the default for p ≤ 8 (break-even rotation efficiency about 13% at p = 8);
  rotation as the default for p ≥ 12 (break-even 4–5%). The crossover near p ≈ 10 is left
  to autotune, as the design doc already plans (§4).
- The f64 dense path must be a hand-written comptime-p kernel: the library offers only its
  scalar path for f64 (no FP64 MMA), which the model puts 2.2–2.6× below the hand-written
  kernel. An FP64 tensor-core path would lift dense GEMM by up to about 2.6× at p ≥ 8
  (1.3× at p = 8 on the H100, which sits at its ridge), but CubeCL does not have one.
- The pinned CubeCL 0.10.0 cannot run f64 on CUDA at all. Before Phase 4, either move the
  workspace pin to 0.11 once it is released (a separate decision; the CubeCL API changes)
  or confirm that `--force-f64` works on 0.10.

What would change this: a measured rotation M2L efficiency (it moves the crossover p
directly), a CUDA measurement of the hand-written f64 kernel (it replaces the central
efficiency), and the O(p⁴) memory of dense operators at high p (design doc §9.1), which
favours rotation independently of speed.

## CubeCL 0.11.0-pre.4

Phase 4 T2, 2026-10-03 (brief: [docs/phase4/T2-cubecl-011.md](../../docs/phase4/T2-cubecl-011.md)).
The workspace pin moved to `cubecl =0.11.0-pre.4`, `cubek-matmul =0.3.0-pre.4` and
`cubek-std =0.3.0-pre.4` (the cubek pre-release whose manifests pin `cubecl =0.11.0-pre.4`),
and the spike was ported to it. Raw output:
[results-m3max-0.11.md](results-m3max-0.11.md) (same machine, macOS 27.0.1, rustc 1.99.0,
every BLAS thread variable set to 1, runs outside the macOS sandbox, no other build running,
1-minute load average 2–6 at each start, no thermal warning).

**The CPU-runtime figures of Phase 0 above are superseded by the measurements in this
section, not carried over.** 0.10.0 JIT-compiled CPU kernels through MLIR at LLVM
optimisation level 0 (`cubecl-cpu` 0.10.0, `src/compiler/module.rs:100`:
`ExecutionEngine::new(&self.module, 0, &[], true)`); 0.11.0-pre.4 compiles them through
`cubecl-llvm` with the `default<O3>` pipeline, a new scheduler and fused multiply-adds.
Design §6.1's "about 1% of CPU peak" for the library and "4–26%" for the hand-written
kernels were measured at level 0. The Metal figures above remain valid; they changed by
at most the run-to-run variance, except where noted below.

### Summary

- **Every kernel passes on 0.11.** `cargo test -p nd-fmm-spike-cubecl-gemm --release`
  passes (both hand-written kernels against the reference on the CPU runtime, f32 and f64,
  every guard shape), and all 174 measured results of the new sweep pass the spike's check
  (f32: at most 7.9e-7; f64: at most 6.8e-16). Tolerances and algorithms are unchanged.
- **Metal f32: no regression.** 90 cells, ratio new/old 0.93–1.51. Library CMMA (`Auto`)
  reaches 3.7–4.9 TFLOP/s for p ≥ 8 and B ≥ 1e4 (0.10.0: 3.5–4.4); the hand-written
  kernel still wins at p = 4 (3.1 TFLOP/s at B = 1e5 against 0.29 for the library).
  Cells above +25% were repeated three times against a same-day 0.10.0 build: the
  small-B gains are real (`tiled-smem` p = 4, B = 1e3: 1.40×; CMMA p = 8, B = 1e3:
  1.41–1.42×); the p = 16, B = 1e5 gains (1.29–1.30×) were the low 0.10.0 sweep, not 0.11
  (same-day ratio 0.94–1.03).
- **CPU runtime, library: 1.3–2.8× faster** (f64 `double_unit` 16–25 GFLOP/s, 2–3% of
  peak; `Auto` 4–16 GFLOP/s), and the library's f32 kernels now compile (longest first
  launch 32 s; 0.10.0: over 5 minutes, unfinished).
- **CPU runtime, hand-written kernels: a confirmed regression.** 42 of 48 cells are
  slower (ratio 0.12–0.92); only B = 1e5 at p ≥ 12 is faster (`cols` 1.3–1.7×, `rows`
  0.8–1.2×). Three repeats and a same-day 0.10.0 control confirm it (0.10.0 reproduces its
  file to within about 15%; 0.11 is 0.11–0.85× of it outside B = 1e5, p ≥ 12). The
  best hand-written f64 kernel per case now reaches 5–147 GFLOP/s (0.7–19% of the 778
  GFLOP/s peak) against 32–200 (4–26%). The cause is how multi-unit launches are
  scheduled, not the generated code: a single unit runs the GEMM 2.5× (f64) to 3.0×
  (f32) faster than on 0.10.0, and a 1-unit launch costs 2 µs (0.10.0: 6 µs), but a
  32-unit launch costs 200–250 µs (0.10.0: 85 µs), and 0.11 timings vary by up to 2.5×
  between runs where 0.10.0 mostly varies by a few per cent ("How the CPU runtime maps a
  launch" below). T3 must take this into account for decision 10.
- **f64:** Metal reports none (measured); the CPU runtime reports it (measured);
  0.11.0-pre.4 registers it for CUDA (source, below). `--force-f64` is no longer needed.
- **fma:** 0.11 fuses `a * b + c` into a fused multiply-add on every backend, CPU
  included. CPU-runtime f64 results are therefore no longer bit-identical to an unfused
  reference (0.10.0: error 0; 0.11: 2.6e-16 to 6.8e-16). This bears on the device
  arithmetic of CONVENTIONS §3.13 (T3).

### `Strategy::Auto` and the 0.11 strategies

`cubek-matmul` 0.3.0-pre.4 splits the strategies into two architectures, each behind a
crate feature (both on by default; the pin turns on `multi-level` only, which holds every
strategy the spike uses):
- `Strategy::MultiLevel(multi_level::Strategy::…)`: the 0.2.0 strategies under their old
  names (`SimpleUnit`, `DoubleUnit`, `SimpleCyclicCmma`, `DoubleCyclicCmma`, …, `Naive`,
  `Gemm`, `GemvUnitPerpendicular`); their display names are unchanged
  (`matmul_simple_unit_max_tile_size`, …);
- `Strategy::Tiled(tiled::Strategy::…)`: new routines on a tile DSL, `Cmma` and `CpuGemm`
  ("register-leaf contraction … tuned for CPU"). Not measured here; `CpuGemm` is a
  candidate for the CPU runtime;
- `Strategy::Auto` (`src/strategy.rs:74`): a storage-tiled operand goes to
  `tiled::Strategy::Cmma`; otherwise it tries `multi_level::SimpleCyclicCmma` and falls
  back to `multi_level::SimpleUnit` when that is `Unavailable`.

Measured: in f32 on Metal, `Auto` still picks CMMA for p ≥ 8 (its times match
`simple_cyclic_cmma` within 8%; 2.0–4.9 TFLOP/s) and the scalar unit path at p = 4
(matching `simple_unit`; CMMA is rejected with "required feature is unavailable: Plane
dimension", as on 0.10.0). On the CPU runtime (plane size 1) the CMMA strategies are
rejected the same way and `Auto` equals `simple_unit`.

### CPU-runtime facts

- **LLVM:** `cubecl-cpu` 0.11.0-pre.4 compiles through the new `cubecl-llvm` crate (pliron
  IR, then `llvm-sys` 231), built against the `tracel-llvm` 23.1.0-3 bundle
  (`tracel-llvm-bundler` 23.1.0-3, LLVM 23; 0.10.0: 20.1.4-7 through MLIR). The bundle
  (`~/.cache/tracel/tracel-llvm-23.1.0-3-macos-AArch64.tar.xz`) is downloaded and unpacked
  by the build script on the first build.
- **Cold build:** `cargo build -p nd-fmm-spike-cubecl-gemm --release` (default features,
  `metal` and `cpu`) in a fresh target directory took 97 s wall clock (724 s CPU); the
  same build of the 0.10.0 spike took 60 s (333 s CPU), measured minutes apart. "Cold"
  means every crate compiled from scratch with the LLVM bundle already downloaded and
  unpacked; the download is not included (T4 measures it).
- **Kernel compile times** (first launch, compilation included; results file, "First
  launch"): the hand-written kernels compile in 10–15 ms each on the CPU runtime (25–30 ms
  on Metal, 65–285 ms for `tiled-smem`). The library's f64 kernels take up to 3.4 s, its
  f32 kernels up to 32 s (`double_unit`, p = 4, B = 1e4); the whole f32 library probe
  (p = 4–16, B = 1e3 and 1e4) finished in 50 s, inside its 20-minute limit. On 0.10.0 the
  f32 library kernels for B = 1e4 did not finish compiling in over 5 minutes.
- **`CUBECL_CPU_STACK_MB`** is still read (`compute/threadpool/scheduler/mod.rs:32`;
  default 64 MB, floor 16 MB) but no longer needed: with it forced to 64 MB, p = 16,
  B = 1e5 ran in f64 (library and hand-written) and f32. The spike still sets 1024 MB,
  which is harmless.
- **Optimisation level O3:** `cubecl-llvm` 0.11.0-pre.4 `src/cpu/jit/engine.rs:141`,
  `const PASS_PIPELINE: &str = "default<O3>"`, run by `LLVMRunPasses` at line 188
  (0.10.0: level 0, see above). Confirmed from the sources built against.
- **fma:** the brief expected no fma contraction on the CPU target, and the lowering
  agrees: `src/shared/to_llvm/math.rs:337–343` puts the `contract` flag on `fadd`/`fmul`
  only for GPU targets (`LlvmTarget::Cpu => FastmathFlagsAttr::default()`). But an
  earlier pass contracts anyway: `cubecl-opt` 0.11.0-pre.4 `InstCombinePass`
  (`src/passes/inst_combine.rs`), registered unconditionally for the CPU at
  `cubecl-llvm` `src/shared/base.rs:425` (and in the C++/MSL and WGSL compilers), rewrites
  every `a * b ± c` whose product has no other use into an `FmaOp`, which lowers to
  `llvm.fmuladd` (`math.rs:485`). It does not consult the kernel's fast-math setting.
  Established three ways: the dumped IR of every kernel inspected (`reg_gemm_kernel` in
  f32 and f64, two library kernels) has `llvm.fmuladd` and no separate `fmul`; the
  AArch64 backend emits `llvm.fmuladd` as a fused `fmla` (LLVM semantics, inferred, not
  disassembled); and the CPU-runtime f64 results changed from bit-identical to the unfused
  reference (0.10.0) to 2.6e-16–6.8e-16 relative error, in every case. The same-day 0.10.0
  build still gives 0.
- **Target CPU:** the O3 pipeline runs **without** a target machine
  (`LLVMRunPasses(module, passes, null, …)`, `engine.rs:188`), and the module carries no
  target triple, data layout, `target-cpu` or `target-features` (checked in the dumped
  `llvm.opt.ll`). So the IR-level vectorisers see no target: the optimised IR contains only
  the vector widths the kernel wrote (`<4 x double>` from `Vector<f64, 4>`; `<8 x double>`
  and its halves in the library), and no loop or SLP vectorisation of scalar code. Code
  generation is by ORC `LLJIT` built with the default builder
  (`LLVMOrcCreateLLJIT(…, null)`, `pliron-llvm` 0.18.0 `src/llvm_sys/lljit.rs:136`), after
  `initialize_native()` (`engine.rs:62`); LLVM's default `LLJITBuilder` uses
  `JITTargetMachineBuilder::detectHost()`, i.e. the host triple, `getHostCPUName()` (an
  Apple M-series CPU here) and the host features, NEON included (inferred from LLVM's
  documented behaviour, not disassembled). Explicit `Vector<T, N>` lanes therefore become
  NEON instructions; scalar code stays scalar. How it was established: the IR was dumped
  with `CUBECL_DEBUG_PLIRON` from a scratch build of the spike's sources with
  `cubecl-cpu/pliron-dump` (the feature cannot be enabled through `cubecl` in this
  workspace, because `cubecl-wgpu`'s `pliron-dump` needs a `cubecl-spirv` release that does
  not exist).

### How the CPU runtime maps a launch

Confirmed from the 0.11.0-pre.4 sources:
- **Cubes are loops inside each unit.** The CPU entry point wraps the kernel body in
  loops over `CUBE_POS_Z`, `_Y`, `_X` (`cubecl-llvm` `src/cpu/entrypoint.rs:277` ff.), so
  each unit runs every cube in turn; with shared memory and more than one unit, a cube
  barrier separates consecutive cubes (`entrypoint.rs:127`).
- **One task per unit.** `Threadpool::execute_data` (`cubecl-cpu`
  `src/compute/threadpool/mod.rs:90`) sends one task per unit of the cube (x, y, z) to the
  scheduler. The `Dispatcher` scheduler starts one worker thread per logical CPU, each
  pinned to its core where the OS allows it (16 here, 12 performance and 4 efficiency
  cores; on macOS the pinning is only a hint, which Apple silicon rejects, per
  `src/compute/affinity/macos.rs`), and:
  - for a kernel with more than one unit that uses `sync_cube` or shared memory
    (`needs_parallelism`, `cubecl-llvm` `src/shared/base.rs:263`), grows the pool to one
    thread per unit and gives unit i its own worker (`mod.rs:85`, `dispatcher.rs:58`), so
    every unit of a cube runs concurrently;
  - otherwise sends each unit to the worker with the shortest queue (`dispatcher.rs:64`),
    so a cube with more units than workers runs in rounds, and a unit may land on an
    efficiency core. Idle workers poll for 200 µs, then block (`dispatcher.rs:111`).
  So a unit has a thread of its own only in kernels with barriers or shared memory.
- **A plane is one unit:** `PLANE_DIM = 1` (`entrypoint.rs:243`).
- **`sync_cube` is a spin barrier:** two atomic counters and a spin-loop hint
  (`src/cpu/synchronization.rs:44`).
- **SIMD** comes only from `Vector<T, N>` (Line) types and LLVM code generation inside
  one unit's code; there is no target-aware vectorisation at IR level (above).
- **Reported limits:** `max_units_per_cube` and each `max_cube_dim` are now the available
  parallelism, 16 (`src/runtime.rs:158`; 0.10.0: `u32::MAX`); the CPU runtime does not
  enforce them (no `validate_units` call in `cubecl-cpu`), so the spike's 32-, 73- and
  256-unit cubes still run. `max_shared_memory_size` is now the L1d size (64 KB reported,
  the efficiency cores' figure; 0.10.0: derived from system memory).

These probably explain the regression of the hand-written kernels: their cubes have 7–73 units
(`tiled-reg-rows`, one unit per 4-row block) or 32 (`tiled-reg-cols`); each unit becomes
a channel message to a pooled worker, a launch waits for its slowest unit (which may be
on an efficiency core or in a second round), and idle workers park after 200 µs. The
generated code itself is faster (single-unit probe: 2.5–3.0×). Inferred from the code
and the probes; the scheduler was not instrumented. For Phase 4 kernels on the CPU
runtime, the likely good shape is at most 12–16 units per cube with the work spread over
the cube count; that is a question for T3, not settled here.
